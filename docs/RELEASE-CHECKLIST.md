# Чек-лист перед запуском на боевом сервере (этап 8)

Составлен в конце этапа 7 из `docs/DEFERRED.md` и `docs/BACKEND-DEV.md`. Пункты идут в порядке выполнения: каждый следующий опирается на предыдущие. У каждого пункта три части: **что сделать**, **где описано**, **как проверить**. Отмечайте `[x]` только после проверки.

Все секреты (пароли, ключи, PFX) задаются переменными окружения сервера или хранилищем секретов; в репозиторий они не попадают. Имена переменных: секция и ключ через двойное подчёркивание (`Smtp:Host` → `Smtp__Host`).

Что приложение проверяет само при старте вне Development и Testing (оно **не запустится**, если что-то не так): ключ JWT, сертификат Data Protection, настоящий SMTP (`Smtp:Host`, не `Security: None`), нетестовый секрет Turnstile, `Frontend:BaseUrl` по https и не localhost, настроенное хранилище файлов, сроки обращений и уроков по ТЗ. Отказ при старте в журнале называет причину.

## 1. VPS и окружение

- [ ] **Сервер и образ.** Купить VPS (бюджет на серверы — открытый вопрос, раздел 16.3 ТЗ). Образ приложения на .NET 10 (`mcr.microsoft.com/dotnet/aspnet:10.0`, на Debian: tzdata уже есть, на Alpine нет). Перед приложением Nginx с TLS. PostgreSQL 17 отдельным сервисом (или управляемым). Для приложения `Hangfire:Enabled=true` (по умолчанию) и **один** экземпляр, пока нет Redis (пункт 11).
- **Где описано:** `DEFERRED.md` («Платформа: .NET 10», «Часовые пояса в Docker-образе», две записи про tzdata); `BACKEND-DEV.md`, раздел 1 (база) и «Фоновые задачи».
- **Как проверить:** `docker run --rm <образ> ls /usr/share/zoneinfo/Asia/Dushanbe` находит файл; письмо-напоминание об уроке приходит со временем в поясе пользователя, а не в UTC; `GET /api/v1/skill-categories` отвечает 200 по https.
- [ ] **Среда.** `ASPNETCORE_ENVIRONMENT=Production`. Настройки для разработки (сокращённые сроки `Cases:*` и `Lessons:*`, тестовый секрет Turnstile, пустой SMTP) в Production приложение не примет; `Hangfire:Enabled=false` оно не запрещает, но на боевом сервере значение всегда `true` (иначе не работают фоновые задачи, письма и ночная уборка).
- **Как проверить:** `/dev/seed-staff`, `/dev/seed-admin`, `/dev/livekit` отвечают 404 (проверяет тест `The_admin_seed_does_not_exist_outside_development`); приложение стартует.

## 2. Домен и TLS

- [ ] **Домен и сертификаты.** Домены для фронтенда, API, хранилища файлов (адрес, который видит браузер) и LiveKit. TLS-сертификаты на всех (Let's Encrypt). Прокси передаёт `X-Forwarded-For` (см. пункт 10).
- [ ] **Адреса в приложении.** `Frontend__BaseUrl=https://<фронтенд>` (по нему строятся ссылки в письмах и CORS для хранилища и API), пути ссылок при необходимости (`Frontend__StaffInvitationPath` и др.). В Production адрес **не** может быть http или localhost.
- **Где описано:** `BACKEND-DEV.md`, «Ссылки из писем» и раздел про хранилище (`Frontend:BaseUrl`, CORS); `FRONTEND-ADMIN.md` (страницы приглашения и привязки).
- **Как проверить:** запрос на сброс пароля приходит письмом со ссылкой на боевой домен, ссылка открывается; из браузера фронтенда проходят запросы к API (CORS не ругается).

## 3. Настоящий SMTP

- [ ] **Что сделать.** Завести почтовый сервис (домен отправителя с SPF, DKIM, DMARC). Задать `Smtp__Host`, `Smtp__Port`, `Smtp__Security` (`StartTls` 587 или `SslOnConnect` 465), `Smtp__User`, `Smtp__Password`, `Smtp__FromAddress`, `Smtp__FromName`. Mailpit и консоль в Production не работают, `Security: None` для удалённого сервера запрещён.
- **Где описано:** `BACKEND-DEV.md`, «Фоновые задачи (Hangfire), почта и Mailpit» (таблица настроек, раздел про Gmail); `DEFERRED.md` (сбойные письма, алерт).
- **Как проверить:** зарегистрировать тестовый аккаунт на настоящий адрес: письмо с кодом и ссылкой приходит, не попадает в спам (проверить заголовки SPF/DKIM у получателя). Сбойные письма видны в панели Hangfire («Failed»).

## 4. Ключи Turnstile

- [ ] **Что сделать.** В панели Cloudflare создать виджет для боевого домена: ключ сайта идёт во фронтенд, секрет в `Turnstile__SecretKey`. Тестовый секрет вне Development приложение не принимает. Фронтенд передаёт `captchaToken` в `register`, `login`, `forgot-password`.
- **Где описано:** `BACKEND-DEV.md`, «Капча (Cloudflare Turnstile)»; `DEFERRED.md` (проверка `action` и `hostname` не делается; капчи нет на `login/2fa`, `resend-confirmation`, `reset-password`).
- **Как проверить:** регистрация с виджетом проходит; запрос без `captchaToken` даёт 400 `captcha_required`; с чужим или просроченным токеном 400 `captcha_invalid`.

## 5. Сертификат Data Protection и его бэкап

- [ ] **Что сделать.** Выпустить **отдельный боевой** сертификат (PFX, RSA 3072; не dev-сертификат). Передать в приложение `DataProtection__CertificateBase64` и `DataProtection__CertificatePassword` (не `CertificatePath` одновременно). Сразу положить PFX и пароль в **два независимых защищённых места** вне сервера (пароль отдельно от файла).
- [ ] **Бэкап как пара.** Копия БД и копия сертификата хранятся вместе: БД без сертификата бесполезна (переписка и токены писем не расшифруются). Старые сертификаты хранить всегда. Включить в **ежемесячный тест восстановления**: ключи из копии БД расшифровываются сохранённым сертификатом.
- [ ] **Не менять сертификат «на лету».** Порядок замены (`DataProtection:PreviousCertificates`) ещё не сделан: сделать до первой плановой замены, до этого сертификат не менять. Срок сертификата: за 30 дней до конца приложение пишет предупреждение при старте, поставить напоминание в календарь.
- **Где описано:** `BACKEND-DEV.md`, раздел 2.1 («Бэкап: обязательно»); `DEFERRED.md` (ротация, боевой сертификат); раздел 11 ТЗ.
- **Как проверить:** приложение стартует; восстановить копию БД на тестовом стенде с сохранённым PFX и убедиться, что отправленное ранее сообщение читается; копии лежат в двух местах и открываются.

## 8. LiveKit с TURN на 443/TLS

- [ ] **Что сделать.** Отдельный VPS для LiveKit (не локальный `node_ip: 127.0.0.1`), домен и TLS, **свои** ключ и секрет (не `devkey`; секрет не короче 32 символов), TURN на 443/TLS, чтобы звонок проходил при закрытом UDP. В приложении: `LiveKit__Url=wss://…`, `LiveKit__ApiKey`, `LiveKit__ApiSecret` (при необходимости `LiveKit__ApiUrl`). В LiveKit адрес webhook: `https://<API>/api/v1/webhooks/livekit`.
- **Где описано:** `DEFERRED.md` («Этап 2: проверка видео на VPS» и «Технический долг до релиза»); `BACKEND-DEV.md`, «LiveKit: прототип связки», «Видеокомната: сводный контракт»; разделы 15 и 16.1–16.2 ТЗ.
- **Как проверить:** (1) два участника в уроке видят и слышат друг друга; (2) **звонок через мобильных операторов**; (3) **звонок при заблокированном UDP** (критерий приёмки раздела 15 ТЗ); (4) webhook доходит: `SELECT "Type", "OccurredAt" FROM "LiveKitWebhookEvents" ORDER BY "CreatedAt" DESC LIMIT 5;`, у событий заполнен `ProcessedAt`; (5) урок закрывается задачей и получает итоговый статус (`Completed` / `NoShow` / `Missed`).

## 10. ForwardedHeaders с KnownProxies

- [ ] **Что сделать.** **Настроить `KnownProxies` под боевой reverse proxy.** Код готов (`UseForwardedHeaders` стоит первым в цепочке), но вне Development заголовки `X-Forwarded-For` и `X-Forwarded-Proto` **не принимаются, пока не заданы адреса прокси**: `ForwardedHeaders__KnownProxies__0=<IP прокси, с которого запросы доходят до приложения>` (или сеть: `ForwardedHeaders__KnownNetworks__0=10.0.0.0/24`). Нужен тот адрес, который приложение видит как `RemoteIpAddress` запроса от прокси (для Nginx на этой же машине это `127.0.0.1`; в Docker-сети адрес контейнера Nginx или его сеть). Прокси должен **перезаписывать** заголовок настоящим адресом клиента (`proxy_set_header X-Forwarded-For $remote_addr;` и `proxy_set_header X-Forwarded-Proto $scheme;`), а не дописывать к присланному клиентом. Если перед приложением несколько прокси, задать `ForwardedHeaders__ForwardLimit` (по умолчанию 1). Пока список пуст, приложение пишет в журнал предупреждение, лимиты по IP (вход, регистрация, письма) считаются общими на всех, а в сеансах и аудите виден адрес прокси. Неверный адрес или сеть в настройках останавливают запуск.
- **Где описано:** `BACKEND-DEV.md`, раздел «Адрес клиента за прокси (ForwardedHeaders)»; `DEFERRED.md` (запись про `ForwardedHeaders`; этап 6, шаг 3, п. 5: адрес в аудите). Тесты: `ForwardedHeadersTests`.
- **Как проверить:** с двух разных внешних IP лимит входа считается раздельно; запрос с поддельным `X-Forwarded-For` (присланный клиентом напрямую или через прокси) не меняет адрес: в списке сеансов и в `/superadmin/audit` остаётся настоящий IP клиента (адреса видит только суперадмин); в журнале при старте есть строка «Заголовки X-Forwarded-For и X-Forwarded-Proto принимаются только от: …» с адресом вашего прокси.

## 11. Redis при нескольких экземплярах

- [ ] **Когда нужно.** Только если запускается больше одного экземпляра API. Пока экземпляр один, **Redis не нужен**, но тогда второй экземпляр запускать нельзя. **В коде Redis не подключён.**
- [ ] **Что переносится в Redis:** счётчики Rate Limiter (иначе каждый экземпляр считает свои), троттлинг чата (`ChatThrottle`), реестр соединений SignalR (бэкплейн, иначе отключение по блокировке и снятию работает в рамках одного экземпляра), билеты и сессии панели Hangfire (хранятся в памяти).
- **Где описано:** `DEFERRED.md` (Rate Limiter; чат; этап 6, шаг 6, п. 2; этап 7, шаг 7, п. 1; этап 7, шаг 9, п. 6); раздел 11.1 ТЗ.
- **Как проверить:** с двух экземпляров общий лимит входа срабатывает на суммарном числе запросов; заблокированный пользователь теряет соединение SignalR на любом экземпляре; панель Hangfire, открытая на одном экземпляре, не требует нового билета на другом.

## 12. Включение DeleteOrphans после первого отчёта

- [ ] **Что сделать.** По умолчанию сверка бакета **только пишет отчёт** (`Maintenance__BucketReconciliation__DeleteOrphans=false`). Только после этого включить `Maintenance__BucketReconciliation__DeleteOrphans=true` и перезапустить.
- **Где описано:** `BACKEND-DEV.md`, «Уборка, права БД и отзыв запросов» (таблица настроек и порядок для боевой среды); `DEFERRED.md` (этап 7, шаг 9: сверка смотрит только вложения).
- **Как проверить:** в отчёте `mode: report`, `deleted: 0`, список образца (`sample`) состоит из ключей вида `exchanges/…`; после включения следующий отчёт `mode: delete`, `failed: 0`, файлы со строкой в `Attachments` остаются; вложения чатов по-прежнему открываются.
