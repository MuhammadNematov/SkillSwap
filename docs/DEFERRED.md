# Отложенные задачи

## Этап 2: проверка видео на VPS (отложено до покупки сервера)

На этапе 2 LiveKit поднимается локально в Docker (dev-режим): проверяем выдачу токенов и подключение к комнате.

Отложено, пока нет VPS (бюджет на серверы — открытый вопрос, раздел 16.3 ТЗ):

- [ ] Поднять LiveKit + TURN на VPS (порт 443/TLS).
- [ ] Проверить звонок через мобильных операторов (раздел 16.1, этап 2; риск из раздела 16.2).
- [ ] Проверить звонок при заблокированном UDP (критерий приёмки раздела 15).

## Платформа: .NET 10

Проекты на `net10.0` (решение от 2026-11-17). Docker-образы (`mcr.microsoft.com/dotnet/sdk:10.0` и `aspnet:10.0`) и CI (`actions/setup-dotnet` с `dotnet-version: 10.0.x`) тоже должны быть на .NET 10.

Технический долг, который нужно закрыть до релиза:

- [ ] LiveKit, этап 5: токен только участникам сессии и только в её окне (сейчас dev-эндпоинт выдаёт любой тестовый токен без входа); удаление комнаты через LiveKit API при закрытии окна; сборка интервалов присутствия из `LiveKitWebhookEvents` (поле `ProcessedAt` пока пусто) и итог урока по таблице раздела 6.3 ТЗ.
- [ ] LiveKit, боевой сервер: отдельный VPS, свои ключ и секрет (не `devkey`), TURN на 443/TLS, адрес webhook на боевой API по https. Локальный `livekit.yaml` для этого не годится (`node_ip: 127.0.0.1`).

- [ ] Turnstile: получить настоящие ключи в панели Cloudflare (сайт и секрет) и задать секрет в окружении боевого сервера (`Turnstile__SecretKey`). Приложение не запустится с тестовым секретом вне Development.
- [ ] Turnstile: проверка привязки токена к действию (`action`) и домену (`hostname`) не делается. Токен, решённый на одной форме, технически пригоден для другой (но токен одноразовый). Для привязки фронтенд должен задавать `action` в виджете, а бэкенд сверять его с эндпоинтом.
- [ ] Капча стоит на register, login и forgot-password (как заказано). `login/2fa`, `resend-confirmation` и `reset-password` без капчи, их защищают лимиты частоты и блокировка аккаунта.

- [ ] Завершённый сеанс (из списка сеансов, по выходу или после сброса пароля) теряет возможность обновлять токен сразу, но его уже выданный access-токен действует до 15 минут (то же, что и для блокировки пользователя в разделе 15 ТЗ). Если нужно мгновенно, придётся проверять сеанс на каждом запросе (дополнительный запрос в БД или кэш в Redis).
- [ ] Утечка по времени в `/auth/forgot-password`: статус и тело одинаковы, но у существующего email ответ чуть медленнее (отправляется письмо). Rate Limiter её не закрывает. **Закрыть, когда подключим Hangfire: отправка письма в фоне.**
- Решено: `deviceInfo` в списке сеансов остаётся сырой строкой User-Agent, читаемое название («Chrome на Windows») разбирает фронтенд.


- [ ] Ключи Data Protection лежат в БД без защиты сертификатом (раздел 10.3 ТЗ). Нужен сертификат вне БД и бэкап.
- [ ] `ConsoleMailSender` заменить на SMTP: в письмах токены.
- [ ] Письма на таджикском: пока отправляется английский текст, перевод — после вычитки носителем.
- [ ] Согласия при регистрации (`AcceptTerms`, `AcceptChatModeration`) проверяются, но нигде не сохраняются: в таблице `Users` в ТЗ нет полей для них. Решить, нужно ли хранить факт и дату согласия.
- [ ] За прокси (Nginx) настроить `ForwardedHeaders` **с перечнем доверенных прокси** (`KnownProxies`/`KnownNetworks`). Без этого все клиенты выглядят как один IP: лимиты по IP (вход, регистрация, письма) станут общими на всех, а в списке сеансов будет адрес прокси. Включать `X-Forwarded-For` без списка доверенных нельзя: заголовок подделывается, и лимиты по IP обходятся.
- [ ] Счётчики Rate Limiter хранятся в памяти процесса: при нескольких экземплярах API каждый считает свои, а после перезапуска счётчики обнуляются. Перенести в Redis, когда он будет подключён (раздел 11.1 ТЗ).
- [ ] При блокировке пользователя отзывать все его refresh-токены (`RevokeAllForUserAsync` уже есть) — подключить в админке (этап 7).
