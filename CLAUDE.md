# SkillSwap — правила для Claude

Платформа взаимного обмена знаниями. Полное техническое задание: `docs/TZ.md`.
Перед любой задачей читай нужные разделы ТЗ. Если ТЗ и просьба расходятся — спроси, не угадывай.

## Структура репозитория

```
backend/    # ASP.NET Core (.NET 8+), Clean Architecture
frontend/   # React + TypeScript + Vite
docs/       # ТЗ и заметки
```

Сейчас Мухаммад ведёт и бэкенд, и фронтенд сам (друг, который писал фронтенд, вернётся позже). Трогать можно обе части.
Правила ниже действуют для обеих. Когда друг вернётся, ему должно быть легко понять, что изменилось, поэтому:

- **Коммиты бэкенда и фронтенда отдельные**: одна задача, которая затронула обе части, это два коммита.
- **Сообщение начинается с «Backend:» или «Frontend:»** (документация и общие файлы: «Docs:» или «Repo:»), дальше короткое описание того, что и зачем.
- В сообщении фронтенд-коммита, если поменялся контракт с бэкендом, назови эндпоинт или код ошибки.

## Как работаем

- Делаем по этапам из раздела 16.1 ТЗ и маленькими шагами. Один шаг = одна понятная задача (например, «сущность Exchange и её переходы статусов»), а не «сделай весь бэкенд».
- После каждого шага код должен собираться, тесты проходить. Потом коммит.
- Объясняй, что сделал и почему, простыми словами, на русском.
- Не добавляй библиотеки, которых нет в ТЗ, без вопроса.

## Backend

- Clean Architecture: `SkillSwap.Domain`, `SkillSwap.Application`, `SkillSwap.Infrastructure`, `SkillSwap.Api` + тесты (раздел 11.1).
- **Без CQRS и MediatR.** Контроллер вызывает сервис из Application (`ExchangeService`, `SessionService`…).
- Переходы статусов — только методами доменных сущностей по таблицам раздела 9; недопустимый переход → `InvalidStateTransitionException` → HTTP 409.
- Авторизация: ASP.NET Core Identity + JWT (раздел 10.1). Проверка прав — на сервере, ресурсная (участник обмена / модератор с активным grant).
- Расписание и лимиты: транзакция с `SELECT … FOR UPDATE` строк обоих пользователей (раздел 10.2).
- Все даты в UTC. Ошибки — ProblemDetails.
- Каждый эндпоинт из раздела 12 виден в Swagger: Swagger — это договор с фронтендом.
- Секреты только в переменных окружения / user-secrets, никогда в коде.

## Frontend

- Простая структура папок, без FSD, Zustand и автогенерации типов (раздел 11.2).
- Типы ответов пишутся вручную по Swagger бэкенда.
- Пока эндпоинта нет — временные заглушки (mock) в `src/api/`, потом замена на настоящий запрос.
- Все тексты интерфейса через react-i18next (tg, ru, en). Новый текст или код ошибки появляется сразу в трёх файлах `src/i18n/`.
- Запуск dev-сервера: `npm run dev` (прокси `/api`, `/hubs`, `/dev` на бэкенд; HTTPS для проверки с другого устройства включается в `.env`, см. `docs/BACKEND-DEV.md`).
- Папка `frontend/` не содержит собранных файлов (`vite.config.js`, `*.d.ts`, `*.tsbuildinfo`): они в `.gitignore`, конфиг Vite один — `vite.config.ts`.
- **Проверка интерфейса глазами (обязательно).** После любых изменений UI (разметка, стили, тексты, новые экраны) запустить `npm run screens` в `frontend/` (бэкенд и фронт должны работать), открыть нужные снимки из `frontend/screenshots/<роль>/` (светлая и тёмная тема, 1440 и 360 px, мобильное меню) и исправить налезания, обрезанный текст, плохой контраст и горизонтальную прокрутку, прежде чем писать «готово». Один экран: `SCREENS_ONLY=admin SCREENS_FILTER=admin_cases npm run screens`. Скрипт сам входит dev-аккаунтами (код 2FA берёт из `/dev/staff-code`) и выводит список автоматических замечаний; он не заменяет просмотр снимков. Если проверить не удалось, так и сказать, а не писать «готово».
- Тесты логики фронтенда: `npm test` в `frontend/` (встроенный `node --test`, файлы `*.test.ts` рядом с кодом, без браузера; в тестируемых файлах не использовать TS-синтаксис, который Node не умеет «стирать»: параметры-свойства конструктора, enum).
